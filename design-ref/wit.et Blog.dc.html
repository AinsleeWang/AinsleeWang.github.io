寫程式的人為什麼還要寫散文

兩種手藝共用同一種紀律：把想清楚的事，用最少的字說完。

我寫了十一年程式，也斷斷續續寫了十一年的字。很長一段時間，我以為這是兩件互相搶時間的事：一件產出可以執行的東西，另一件只產出感想。後來我發現不是。兩者都在處理同一個問題——如何把腦子裡那團還沒定形的東西，變成別人可以走進去的結構。

程式碼的讀者是機器，也是三個月後的自己。散文的讀者是陌生人，也是三個月後的自己。這兩種讀者都不接受藉口，你只能把話說清楚，或者說不清楚。

刪掉，是同一個動作

重構的第一步通常是刪。刪掉為了「以後可能會用到」而留的抽象層，刪掉三個只被呼叫過一次的 helper。寫作也一樣，第二稿的工作幾乎全部是刪：刪掉為了顯得深刻而留的形容詞，刪掉重複解釋同一件事的第二段。

好的段落和好的函式有同一個特徵：拿掉任何一句，剩下的就站不住。

這不是比喻。我真的會在寫完一篇文章之後，用讀 pull request 的方式再讀一次——這一段在做什麼？它有沒有副作用？它可以被更短的東西取代嗎？多數時候可以。

所以這個網站不分「技術文章」和「生活雜記」。對我來說它們是同一疊稿子，只是輸出格式不同。

TIL：git worktree 讓我不再 stash

同事丟來一個 hotfix，我手上的功能改到一半。以前的流程是 stash、切分支、修完再 pop，然後花十分鐘想剛剛那包東西到底改到哪。worktree 讓兩個分支同時存在於磁碟上的兩個資料夾，什麼都不用收。

bashcopy
# 在 ../hotfix 開一份 hotfix 分支的工作區
git worktree add ../hotfix -b hotfix/login-500

# 修完，刪掉工作區，分支還在
git worktree remove ../hotfix

我的 alias

每次都打完整指令太長，我把它縮成 gwt，順便讓資料夾名字自動跟著分支名走。

.zshrccopy
gwt() {
  git worktree add "../$(basename $PWD)-$1" -b "$1"
}

唯一還會用 stash 的場合：改動小到不值得開一個資料夾，例如只想跑一次 build 看看。
